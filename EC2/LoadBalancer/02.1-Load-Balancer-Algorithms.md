# AWS Load Balancer Algorithms (Routing Algorithms)

A **Load Balancer algorithm** is the strategy used to decide **which backend server (EC2, Pod, Container, VM, etc.) should receive the next request**.

<img width="1536" height="1024" alt="ALB_ALGO" src="https://github.com/user-attachments/assets/e73314c0-2d47-48de-b347-b6dbccc063a5" />


Imagine you have **3 web servers** behind a load balancer.

```
           Users
             |
             |
      +--------------+
      | Load Balancer|
      +--------------+
       /      |      \
      /       |       \
+---------+ +---------+ +---------+
|Server A | |Server B | |Server C |
+---------+ +---------+ +---------+
```

The algorithm decides:

> **"Should the next request go to A, B, or C?"**

---

# 1. Round Robin (Most Common)

## How it works

Requests are sent **one after another** to each server in sequence.

```
Request 1 → Server A
Request 2 → Server B
Request 3 → Server C
Request 4 → Server A
Request 5 → Server B
Request 6 → Server C
```

Architecture

```
                Users
                  |
                  |
          +----------------+
          | Load Balancer  |
          +----------------+
          /      |       \
         /       |        \
        A        B         C

Req1 ---> A
Req2 -------> B
Req3 ------------> C
Req4 ---> A
Req5 -------> B
Req6 ------------> C
```

### Example

Three EC2 instances

```
EC2-1
EC2-2
EC2-3
```

100 requests

Distribution

```
EC2-1 → 34

EC2-2 → 33

EC2-3 → 33
```

Each server receives approximately the same number of requests.

### Best For

* Identical servers
* Same CPU
* Same RAM
* Same application

---

# 2. Weighted Round Robin

Some servers are stronger than others.

Example

```
Server A → 8 CPU
Server B → 4 CPU
Server C → 2 CPU
```

Assign weights

```
A = 4

B = 2

C = 1
```

Now requests become

```
A
A
A
A
B
B
C
```

Then repeat.

Architecture

```
               Load Balancer

                    |

     -----------------------------------

     |               |               |

 Weight=4        Weight=2        Weight=1

 Server A        Server B        Server C
```

### Example

70 requests

```
Server A → 40

Server B → 20

Server C → 10
```

The powerful server gets more traffic.

---

# 3. Least Connections

Instead of counting requests,

The load balancer checks

> Which server currently has the fewest active connections?

Example

Current situation

```
Server A → 100 users

Server B → 40 users

Server C → 15 users
```

New request

```
→ Server C
```

Architecture

```
                Load Balancer

                       |

     -------------------------------------

     |                |                 |

100 Connections   40 Connections   15 Connections

      A                 B                C

                     Next Request
                          |
                          V
                          C
```

### Best For

Long-running sessions

Example

* Banking
* Chat
* WebSocket
* Video conferencing

---

# 4. Weighted Least Connections

Combination of

* Weight
* Active connections

Example

```
Server A

Weight = 5

Current Connections = 50

---------------------------

Server B

Weight = 2

Connections = 20

---------------------------

Server C

Weight = 1

Connections = 5
```

The load balancer considers **both capacity and current load** before routing traffic.

Used in enterprise ADCs like **F5**, **NGINX Plus**, and **HAProxy**.

---

# 5. Least Response Time

The load balancer measures

> Which server responds the fastest?

Example

```
Server A → 45 ms

Server B → 20 ms

Server C → 10 ms
```

New request

```
→ Server C
```

Architecture

```
                 Load Balancer

                        |

------------------------------------------------

|               |                |

45 ms          20 ms            10 ms

 A               B               C

                     New Request
                          |
                          V
                          C
```

Useful when one server is becoming slow even if CPU usage is low.

---

# 6. IP Hash (Source IP Affinity)

The client's IP address is hashed to determine the backend server.

Example

```
Client 10.1.1.15

Hash(IP)

↓

Server B
```

Every time the same client sends a request,

```
10.1.1.15

↓

Server B
```

Architecture

```
Client A (IP1)
        \
         \
          ---> Hash(IP1) ---> Server A

Client B (IP2)
        \
         \
          ---> Hash(IP2) ---> Server C

Client C (IP3)
        \
         \
          ---> Hash(IP3) ---> Server B
```

Useful for

* Session persistence
* Shopping carts
* Banking applications that store session state locally

---

# 7. Random

The load balancer randomly selects a backend.

```
Req1 → Server C

Req2 → Server A

Req3 → Server B

Req4 → Server A

Req5 → Server C
```

Not commonly used in production because traffic may become uneven.

---

# 8. Least Bandwidth

Chooses the server currently consuming the least network bandwidth.

Example

```
Server A → 800 Mbps

Server B → 300 Mbps

Server C → 120 Mbps
```

Next request

```
→ Server C
```

Useful for

* File downloads
* Video streaming
* Large object transfers

---

# 9. Resource-Based (Adaptive)

The load balancer continuously monitors backend health metrics such as:

* CPU utilization
* Memory usage
* Network usage
* Disk I/O
* Response time

Example

```
Server A

CPU = 90%

Memory = 95%

----------------

Server B

CPU = 25%

Memory = 30%

----------------

Server C

CPU = 45%

Memory = 50%
```

The next request is sent to **Server B**, which has the most available resources.

Common in cloud-native environments with advanced load balancers and service meshes.

---

# Comparison Table

| Algorithm                  | Decision Based On             | Best Use Case                  |
| -------------------------- | ----------------------------- | ------------------------------ |
| Round Robin                | Sequential order              | Equal-capacity servers         |
| Weighted Round Robin       | Server capacity               | Mixed-size servers             |
| Least Connections          | Active connections            | Long-lived sessions            |
| Weighted Least Connections | Capacity + active connections | Enterprise applications        |
| Least Response Time        | Fastest server                | Latency-sensitive APIs         |
| IP Hash                    | Client IP                     | Session persistence            |
| Random                     | Random choice                 | Testing or simple environments |
| Least Bandwidth            | Current bandwidth usage       | File and media servers         |
| Resource-Based             | CPU, memory, health metrics   | Dynamic cloud environments     |

---

# Which Algorithms Does AWS Support?

For **AWS Elastic Load Balancing (ELB)**, support depends on the load balancer type:

| AWS Load Balancer                   | Supported Routing Algorithm                                                                      |
| ----------------------------------- | ------------------------------------------------------------------------------------------------ |
| **Application Load Balancer (ALB)** | **Least Outstanding Requests (LOR)**                                                             |
| **Network Load Balancer (NLB)**     | **Flow Hash** (5-tuple hash: source IP, destination IP, source port, destination port, protocol) |
| **Gateway Load Balancer (GWLB)**    | **Flow Hash** to keep packets of the same flow on the same appliance                             |
| **Classic Load Balancer (CLB)**     | Round-robin–style distribution with optional sticky sessions (legacy service)                    |

# Real-World Banking Example

Suppose your banking application has **3 pods** behind an **AWS Application Load Balancer**:

```
                 Users
                   |
            AWS Application
            Load Balancer (ALB)
                   |
      -----------------------------
      |            |             |
   Pod-1          Pod-2         Pod-3
      |            |             |
      +------------+-------------+
                   |
              Keycloak Auth
                   |
             Application Layer
                   |
                Amazon RDS
```

If the application stores **session state locally inside each UXP pod**, a user may log in through **Pod-1**, but subsequent requests can be routed to **Pod-2** or **Pod-3**. Those pods don't have the user's local session, causing authentication failures or unexpected logouts.

Typical solutions include:

* **Enable ALB sticky sessions** (cookie-based session affinity).
* Store session state in a **shared external session store** (for example, Redis or a database), so any pod can process the request.
* Design the application to be **stateless**, relying on tokens (such as JWTs) rather than local in-memory sessions.

For modern cloud-native applications, the preferred long-term approach is to make the application stateless whenever possible, using sticky sessions only when required for legacy applications.

**AWS ALB and NLB do not support all load-balancing algorithms**. AWS supports only a small set of routing algorithms.

## AWS Application Load Balancer (ALB)

ALB currently supports **three** routing algorithms at the **Target Group** level:

| Algorithm                            | Supported | Default    |
| ------------------------------------ | --------- | ---------- |
| **Round Robin**                      | ✅ Yes     | ✅ Default  |
| **Least Outstanding Requests (LOR)** | ✅ Yes     | ❌ Optional |
| **Weighted Random**                  | ✅ Yes     | ❌ Optional |

AWS documentation states that you can configure the target group's routing algorithm as **Round Robin**, **Least Outstanding Requests**, or **Weighted Random**. ([AWS Documentation][1])

> **Note:** `Weighted Random` is a relatively newer addition and supports **Automatic Target Weights (ATW)** for anomaly mitigation. ([AWS Documentation][1])

---

## AWS Network Load Balancer (NLB)

NLB **does not let you choose** a routing algorithm.

It **always** uses a **Flow Hash** algorithm based on:

* Protocol
* Source IP
* Source Port
* Destination IP
* Destination Port
* TCP Sequence Number

The selected target handles that connection for its lifetime. ([AWS Documentation][2])

---

## AWS Gateway Load Balancer (GWLB)

Uses:

* ✅ **5-Tuple Flow Hash**

This ensures all packets belonging to the same flow reach the same appliance. ([AWS Documentation][2])

---

## AWS Classic Load Balancer (CLB) (Legacy)

| Listener Type | Algorithm                  |
| ------------- | -------------------------- |
| HTTP / HTTPS  | Least Outstanding Requests |
| TCP           | Round Robin                |

This is AWS's legacy load balancer and is not recommended for new deployments. ([AWS Documentation][2])

---

## Algorithms **Not Supported** by AWS ELB

AWS ELB **does not support** these common algorithms:

* ❌ Least Connections
* ❌ Weighted Least Connections
* ❌ IP Hash
* ❌ URL Hash
* ❌ Least Response Time
* ❌ Least Bandwidth
* ❌ Resource-Based Routing
* ❌ Consistent Hashing

If you need these algorithms, you typically use a software load balancer such as **NGINX**, **HAProxy**, **Envoy**, or **F5 BIG-IP**.

### Summary

| AWS Load Balancer | Supported Algorithms                                       |
| ----------------- | ---------------------------------------------------------- |
| **ALB**           | Round Robin, Least Outstanding Requests, Weighted Random   |
| **NLB**           | Flow Hash (fixed, not configurable)                        |
| **GWLB**          | 5-Tuple Flow Hash                                          |
| **CLB (Legacy)**  | Round Robin (TCP), Least Outstanding Requests (HTTP/HTTPS) |
