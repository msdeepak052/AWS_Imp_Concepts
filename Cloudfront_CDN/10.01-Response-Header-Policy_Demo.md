# 10.01 - Hands-On Demo: Response Headers Policy in Practice

> Goal: watch CloudFront add, override, and strip HTTP response headers **at the edge**, entirely independent of what `postman-echo.com` itself returns — and see that this happens on a completely different timeline than caching (Note 09) does. Continuation of [Note 09.01](09.01-Cache-Behavior_Demo.md), reusing the exact same `/get` cache behavior. Entirely via the **AWS Console**, no CLI.

---

## 1. Why this reuses 09.01's setup

`postman-echo.com` barely sets any headers of its own beyond the basics (`content-type`, `date`, a Node/Express default or two) — which is actually ideal here. Anything security-related or custom that shows up in the response can only have come from **CloudFront's Response Headers Policy**, not the origin. No new origin or behavior needed — everything in this demo happens by editing the `/get` behavior from 09.01.

> 🧠 **Mental model:** Note 09's Cache Policy and Origin Request Policy govern the two legs *before* CloudFront has a response in hand (what counts as the same request, what gets forwarded to origin). A **Response Headers Policy** operates strictly *after* — once CloudFront already has a response body (from cache or from origin), on its way back out to the viewer. Different stage of the pipeline entirely.

---

## 2. Prerequisite

The `/get` cache behavior + `PostmanEchoOrigin` from [Note 09.01](09.01-Cache-Behavior_Demo.md), still in place on your distribution. If you tore it down, redo 09.01 Section 3 first (just the origin + behavior, the cache/origin-request policy specifics don't matter for this demo).

## 5. Switch to a custom policy — and watch the managed headers disappear

Only **one** Response Headers Policy can be attached to a behavior at a time — switching to a different one doesn't layer on top of the last one, it **replaces** it entirely. This is the same "policies replace, not merge" lesson Note 09.01 taught for Cache Policies, now showing up again here.

### Step 1 — Create a custom Response Headers Policy
1. **CloudFront console** → **Policies** → **Response headers** tab → **Create response headers policy**.
2. **Details**: **Name**: `Demo-ResponseHeaders-Custom`.
3. **Custom headers — optional** → **Add custom header**:
   - **Header name**: `X-Demo-Response`
   - **Value**: `v1`
   - **Override**: **Yes** (so this wins even if something upstream already set the same header name).
4. Leave **CORS**, **Security headers**, and **Remove headers** sections all off for now — Section 6 comes back for CORS.
5. **Create**.

### Step 2 — Attach it
1. **Behaviors** tab → select `/get` → **Edit**.
2. **Response headers policy**: switch from `Managed-SecurityHeadersPolicy` to `Demo-ResponseHeaders-Custom`.
3. **Save changes** → wait for **Deployed**.

## 6. Add CORS to the same custom policy

1. **Policies** → **Response headers** tab → select `Demo-ResponseHeaders-Custom` → **Edit**.
2. **CORS** section → enable **Configure CORS**:
   - **Access-Control-Allow-Origins**: `*`
   - **Access-Control-Allow-Methods**: `GET, HEAD`
   - **Access-Control-Allow-Headers**: `*`
   - **Access-Control-Allow-Credentials**: leave **off** (incompatible with `*` origins by the CORS spec itself).
   - **Origin override**: **Yes**.
3. **Save changes**. (No need to touch the behavior again — same policy, propagates once redeployed.)

```bash
curl -s -D - "$CF_URL/get?id=1" -H "Origin: https://example.com" -o /dev/null
```

You should now see both `x-demo-response: v1` **and** `access-control-allow-origin: *` (plus `access-control-allow-methods`) on the same response — this policy now carries two independent dimensions, exactly like 09.01's cache policy grew from one dimension to two.

> 🧠 This is Note 10 Section 2's CORS row, and directly answers Note 10 Section 3's question: since `postman-echo.com` isn't S3 and sets no CORS headers of its own, there's no ambiguity here about which layer's CORS header wins — CloudFront's is the *only* one in play. (`S3-Simple_Storage_Services/29`'s bucket-level CORS config is the other half of that same question, for an S3 origin specifically.)

## 7. The caching gotcha — headers vs. body follow different rules

This is the one genuinely non-obvious part, and worth testing rather than taking on faith.

1. Request the same URL twice to get a cache **Hit** on the second call:
   ```bash
   curl -s -D - "$CF_URL/get?id=1" -o /dev/null | grep -iE "x-cache:|x-demo-response:"
   curl -s -D - "$CF_URL/get?id=1" -o /dev/null | grep -iE "x-cache:|x-demo-response:"
   ```
   Second call should show `X-Cache: Hit from cloudfront` and `x-demo-response: v1`.
2. **Without touching the cache behavior or the cache key at all**, edit the header's value: **Policies → Response headers → `Demo-ResponseHeaders-Custom` → Edit → Custom headers → change `X-Demo-Response` value from `v1` to `v2`** → **Save changes**.
3. Immediately re-request the **exact same** URL:
   ```bash
   curl -s -D - "$CF_URL/get?id=1" -o /dev/null | grep -iE "x-cache:|x-demo-response:"
   ```

Expected result: `X-Cache` is **still** `Hit from cloudfront` (same cached body, no new origin fetch) — but `x-demo-response` has already flipped to `v2`. The **cached body** and the **response headers policy** are two independent layers: caching decides whether the origin gets re-fetched; the Response Headers Policy is re-applied fresh on *every single response*, hit or miss, with no invalidation needed for a headers-only change.

> ⚠️ **Don't over-generalize this.** This instant-update behavior applies to headers **CloudFront's own Response Headers Policy adds or overrides**. It does *not* apply to headers the **origin** itself sets as part of a cached response body — those genuinely are frozen into that cached object until it expires or is invalidated (Note 18). That's the specific "CORS works sometimes but not always" trap Note 10 Section 3 warns about for an S3 origin with its own CORS config — a different mechanism producing a superficially similar-looking staleness bug, worth not confusing with what you just tested here.

## 8. Managed vs. custom policy, in this demo

- **`Managed-SecurityHeadersPolicy`** (Section 4) is an **AWS managed policy** — sensible security defaults, no authoring needed.
- **`Demo-ResponseHeaders-Custom`** (Sections 5-7) had to be custom — no managed policy bundles "this one specific custom header plus this specific CORS configuration," because, like Note 09.01's cache policy, that combination is inherently application-specific.

## 9. Troubleshooting

| Symptom | Likely cause |
|---|---|
| No headers changed at all after attaching a policy | Distribution still shows **Deploying**, not **Deployed** — wait, then retest |
| `access-control-allow-origin` missing even with CORS configured | You didn't send an `Origin` header in the request — CloudFront's CORS headers are typically only added when the request itself looks like a CORS request |
| Custom header shows the **old** value right after editing the policy | Give it a minute to redeploy; if it's still stale after that, you may be hitting a different edge location's momentarily-stale config propagation, not a caching issue — retry after a short wait |
| Security headers from Section 4 still appearing after switching to the custom policy | The behavior's **Response headers policy** dropdown wasn't actually changed/saved — recheck Section 5, Step 2 |

## 11. Recap

- A **Response Headers Policy** adds, overrides, or removes headers on the way back to the viewer, entirely independent of what the origin sent — Section 4 proved this by adding security headers `postman-echo.com` never set.
- Only **one** Response Headers Policy attaches per behavior at a time — switching replaces the previous one outright, it doesn't merge (Section 5).
- Response Headers Policies apply **fresh on every response, including cache Hits** — a completely different timeline from the cached body itself, which only changes on a Miss or an invalidation (Section 7). Don't confuse this with origin-set headers baked into a cached response, which *do* go stale until invalidated.
- Managed policies (`SecurityHeadersPolicy`) cover common cases; anything combining a custom header with a specific CORS configuration needs a custom policy, same pattern as Note 09.01's cache policies.
